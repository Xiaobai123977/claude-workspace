# 业务拓扑工作规范

按需阅读代码，不扫描密钥、个人配置、依赖目录和构建产物。先查业务入口、数据模型，再追踪数据的生产、装配、消费、返回和持久化。不要从文件名或直接调用关系猜完整业务。只在用户要求实现或修改时修改业务代码。

## 必须完成的数据追踪

图表达的是可跟随数据阅读的业务流程，不是目录或功能卡片清单。先选具体业务入口（用户提交什么、事件如何触发），沿真实数据追踪处理、判断、存储、外部请求、返回和错误分支，再抽象模块。不要先凑模块数再补线。一个模块有多条输入输出时分别列端口和边；调用与返回、不同数据、成功与失败路径分别建边，不能塞进一句模糊“调用处理”。孤立模块必须追踪来源和去向，无法核实则明确 unresolved，不能交付为完整业务。

## 自动深度探索的队列与停止证据

自动深度不是顶层图完成即停止。每轮写出图后检查当前所有没有子模块的内部模块，阅读实现后继续细化有独立步骤的模块，并维护待展开队列。每批子代理完成后立即合并、校验、派发下一批，直到范围内队列清空。

经实际代码核实的单一业务叶子记录 `exploration:{"state":"leaf","reason":"具体函数/代码证据，以及为何已无可独立拆分的步骤"}`，并保留真实 refs；不可见外部或存储黑盒可用 state=external 并说明边界。不能继续时写 state=blocked 与真实阻塞原因，它不会被计为探索完成。不能用“单一用途”“已经完整”这种没有实现依据的文字批量标叶子来跳过探索。

不得为了凑够层级或节点数量生成无意义拓扑。变量赋值、参数绑定、单个表达式和语法包装不能单独充当业务模块；应先核实是否真的存在可独立描述输入、处理、输出的步骤。已到代码级叶子时，说明具体代码位置与停止理由，保留叶子记录，不凭空新增子模块；用户要求继续展开时也应解释不能合理拆分的依据。

自动探索写图后运行 `node .claude/skills/workspace-topology/validate.cjs --explore-auto`；局部范围加 `--modules=id1,id2`。输出的 exploration.frontier 仍有条目就继续，不得报告全量完成；检查通过只证明有停止记录和数据流映射，不能证明语义正确。应用会在成功回复仍有缺口时续发下一批（最多 8 批；连续两轮清单无进展则暂停并明确未完成），不把运行上限冒充完整。

每个模块只有一个业务用途：输入 → 处理 → 输出。顶层建议 5–9 个模块；parent 表示递归拆分，保持 ID 稳定。purpose 和端口说明用中文。inputs/outputs 中每项是一个唯一的数据端口，不能只写“输入/输出”；触发事件、状态变化、错误和副作用也属于数据。

逐项建立明确对应，不得交付“文字说明了去向、图上没有去向”的图：

1. 每项输入都要有来源，每项输出都要有去向。edges 必须以 sourceOutputs 和 targetInputs 精确绑定端点节点的端口字符串，不能依赖 data 描述相似就算连通。一条边可绑定多个端口，同一输出可扇出。
2. 边不限于直接调用。kind 分为 call（调用）、data（含中介的数据传递）、storage-write、storage-read、side-effect（请求外部服务）、return（返回结果）。方向按实际数据流，调用请求与返回结果是不同方向的边。
3. 数据经列表/字典/事件/共享状态等中介从 A 到 B，即使没有直接调用也必须画出数据边。refs 给出生产/装配及消费证据；必要时将中介建为模块。不要把一个函数返回就当成业务数据终点。
4. 写文件、DB、缓存必须有到存储节点的边；调用 LLM、网络服务必须有到外部黑盒的边，需要结果时还有返回边。不得用 uncertain 或 terminal 掩盖已能追踪的关系。外部和数据库节点不会自动豁免数据检查。
5. 只有确实跨出当前分析范围或终止，才用节点 boundaries 说明具体端口的边界。每条边界必填 direction、port、kind、reason、refs：entry 仅用于输入触发源；terminal 仅用于已证明没有项目内消费者的输出（如最终审计归档）；external 仅用于外部/存储黑盒不可见的一侧；parent 绑定父节点同方向的 parentPort（必须真实存在）表示子图边界，不要为连通而虚构兄弟调用；unresolved 记录未核实来源/去向，检查仍不通过。
6. 不能因无入边/出边就随意加边或标终端。逐个核实所有零入边、零出边节点的依据。真实终点可标 kind=terminal，但这不替代端口级边界和证据。inputs/outputs 不可为空，终态输出应如实列明。未展开模块可保持黑盒，但对外输入输出仍必须闭合。
7. 已实现的每个节点、每条边、每个边界都有项目内真实代码 refs。计划设计可 refs=[]，必须标 status=planned 并遵守下文双向开发协议。不能虚构文件、行号或执行结果；不确定写 uncertain 或 unresolved，保留草稿而不是宣称完整。

## 文件协议

写入 `.claude/workspace-topology.json`，UTF-8 严格 JSON。version 保持 1，新增 flowVersion:1 表示启用显式数据流协议。旧图先保留原 ID 和结构，补齐端口绑定，不能仅加 flowVersion 就宣布完成。

最小闭合示例（必须替换为项目真实代码证据）：

```json
{
  "version": 1,
  "flowVersion": 1,
  "title": "项目业务拓扑",
  "description": "基于实际代码的静态数据流分析，未运行真实业务请求。",
  "nodes": [
    {"id":"request","label":"接收请求","purpose":"校验用户提交的数据","kind":"module","inputs":["用户请求"],"outputs":["已校验请求"],"refs":[{"path":"src/entry.ts","line":1}],"boundaries":[{"direction":"input","port":"用户请求","kind":"entry","reason":"HTTP 路由接收外部请求","refs":[{"path":"src/entry.ts","line":1}]}]},
    {"id":"audit","label":"审计归档","purpose":"追加只读审计记录","kind":"terminal","inputs":["待归档请求"],"outputs":["归档审计记录"],"refs":[{"path":"src/audit.ts","line":1}],"boundaries":[{"direction":"output","port":"归档审计记录","kind":"terminal","reason":"审计归档是流程终态，已检查写入点和项目内读取方，未发现业务消费者","refs":[{"path":"src/audit.ts","line":12}]}]}
  ],
  "edges": [
    {"id":"request-audit","source":"request","target":"audit","kind":"data","label":"提交审计","data":"已校验的请求用于审计归档","sourceOutputs":["已校验请求"],"targetInputs":["待归档请求"],"refs":[{"path":"src/entry.ts","line":20},{"path":"src/audit.ts","line":1}]}
  ]
}
```

node.kind 允许 module / external / database / terminal。ID 使用字母、数字、下划线、点、冒号、连字符；节点/连接 ID 各自唯一；source/target/parent 必须存在，parent 不得循环。端口字符串在本节点内唯一。refs 为项目内正斜杠相对路径及正整数行号。最多 250 节点、600 边、1 MB。达到限制时明确保留待探索范围，不虚构全量覆盖。

## 交付检查（不可跳过）

写图后在项目根目录运行：

```sh
node .claude/skills/workspace-topology/validate.cjs
```

该命令和 GUI 共用解析及完整性检查，退出码 0 才是映射检查通过；退出码 1 必须继续处理 issues。若运行环境没有 Node 或命令失败，如实说明未完成验证，不能凭口头自检宣布通过。禁止修改检查器、删除端口或随意声明边界来绕过检查。

检查全部输入来源、输出去向、边端口绑定、边类型、层级边界与 refs。逐项核实中介依赖、外部请求、存储读写、失败路径。未解决的缺口保留 unresolved / uncertain，向用户报告“草稿，未通过完整性检查”。代码引用存在和图映射闭合只证明结构，不能证明业务语义真实，仍须核对代码。

并发探索时，各子代理返回各自端口、边、边界和真实代码证据；主模型统一核对跨模块端口、合并、写图、运行检查。子代理全部返回不等于主任务完成。最终说明实际覆盖范围/深度、零入边及零出边清单、明确的入口/终点/层级边界，以及检查结果和未解决项。

## 局部讨论与维护

按选区版本、ID、refs 确定范围，先读关联代码。询问/批注默认不修改代码。认可局部设计不等于完整图已通过检查，不替代测试或工具权限。修改业务逻辑后同步更新受影响端口与边，不重写无关结构。层级细化保留父模块边界；跨层数据通过显式 parent 边界或真实连接表达。


## 双向开发：需求 → 拓扑 → 代码 → 拓扑

拓扑同时承载设计契约和已实现的事实，不必等项目写完才建图。新项目从用户需求设计 inputs/outputs、边、边界和验收条件，再按模块逐步实施。已有代码和未来设计可共存于同一图，不另建两份会互相漂移的图。

### 生命周期字段

节点和连接可写 `status: "planned" | "implemented"`。省略时按旧版已有实现处理，仍要求真实代码证据。新规划的节点与边必须明确 planned，refs 可为空，不能虚构未来文件行号；已实现的节点/边必须有真实 refs。父模块部分实现时保留 planned，不能因为部分子模块完成就把父模块算完成。

计划节点必须列出 `acceptance: ["可检验的输入、输出、错误路径或业务约束", ...]`，而非“正常运行”这样的空泛描述。所有设计输入输出仍须绑定真实的设计端口与边界；planned 不豁免数据流闭合。

节点可记录 `verification: {"status":"pending|passed|failed", "summary":"实际执行结果及限制", "commands":["实际运行的验证命令"]}`。这是 AI 的执行报告而不是程序认证；只有实际运行验证才能填 passed/failed，未运行用 pending。代码写入不等于验证通过；不得把设计通过、implemented、passed 混成一个完成状态。只读核对不得将过去测试记录冒充本次验证；相关代码变化后重测或把原记录降为 pending。

### 三种工作方式

- design：从需求设计或局部补全模块与数据契约。保留已存在的代码事实和稳定 ID；已有实现与用户新需求矛盾时保留事实并明确待调整内容。只写拓扑，不写业务代码。计划端口边界说明设计依据，无须伪造代码证据。运行 `node .claude/skills/workspace-topology/validate.cjs --design`；通过仅代表设计映射闭合。
- implement：先读所选范围、依赖边界和 acceptance。按依赖顺序实现，不只生成占位文件，不假装完成外部接入。每完成一个模块同步更新 refs、对应边及状态；剩余模块保留 planned。依据验收条件真实验证并记录，最后同时报告设计检查和默认实现检查的结果。用户未选中的范围保持不变；需要扩展范围时明确说明。
- sync：读代码核对与更新图，不改业务代码。真实实现补 refs；缺失的 planned 设计必须保留，不能删掉来“对齐”。代码偏离既定契约时用 uncertain 明确差异，不能悄悄把设计改成错误的代码行为。相关测试未知则 pending。

普通开发任务中，只要项目已有拓扑，就在改代码前按需定位相关模块，开发后同步更新受影响节点、边、验收条件与实际验证记录。不要为只读问答改图，不自动启动额外模型请求。修改前重读最新图、核对版本，保留他人变更。

检查器默认仍要求实现证据，planned 节点/边会报告 pending-code 并返回非零。`--design` 不因 pending-code 或实现测试失败而否定设计闭合，但这些仍在 issues 中如实报告；缺失端口、错误边界、未明确的需求、失效引用仍会导致设计检查失败。测试失败不阻止重新按图修复代码，默认检查仍报告失败。界面会分别显示设计闭合和待实现范围；设计闭合不能宣传成项目已开发完成。
